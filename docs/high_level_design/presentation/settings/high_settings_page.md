# 設定画面 概要設計書（退会）

## 目的

ユーザーがアプリから退会できるようにする。退会すると、次のデータをすべて削除する。

- Firebase Authentication のユーザー
- Firestore のそのユーザーのデータ（`users/{uid}` 配下のフォルダ・単語・学習結果・設定）
- Firestore のそのユーザーのアカウント情報（`accounts/{uid}`。開発者フラグ・サブスク・規約同意）
- 端末内（SQLite）のそのユーザーのデータ（同じ端末で使っている他のアカウントのデータは残す）

退会後も、退会済みであることの記録（`deleted_accounts/{uid}`）だけは残す（「退会済みの記録」）。
ほかに、規約への同意の履歴（`consent_logs/{uid}`）も残す（`legal_consent.md` §退会時）。

## 削除の方式

- Firestore と Authentication の削除は、Cloud Functions の関数 `deleteAccount` に任せる。アプリはこの関数を**1回呼ぶだけ**にする
- 関数は、呼び出したユーザー本人（ログイン情報の uid）のデータだけを削除する。最初に退会済みの記録を作り、次に Firestore のデータを削除し、最後に Authentication のユーザーを削除する
- 関数は何度呼んでも同じ結果になるようにする。すでに消えているデータやユーザーは飛ばして、成功を返す
- 関数の成功を受け取ってから、アプリが端末内のデータを削除する
- 退会の前にパスワードの再入力（再ログイン）は求めない。確認ダイアログ2回で意思を確認する

## 画面構成

- 設定画面の「アカウント」の項目で、「ログアウト」の下に「退会」を配置する
- 「外観」と「アカウント」の間に、見出し「このアプリについて」と「利用規約」「プライバシーポリシー」の項目を置く（動作は `legal_consent.md` §設定画面から規約を読む）
- 「退会」は取り消せない操作であることが分かるように、文字を赤色（エラー色）にし、人の削除が分かるアイコンを付ける

## 退会の流れ

1. 設定画面で「退会」を押下すると、確認ダイアログを表示する
2. 確認ダイアログで「OK」を押下すると、最終確認ダイアログを表示する
3. 最終確認ダイアログで「OK」を押下すると、退会処理を始める。処理中はローディングを表示し、他の操作（戻る操作を含む）をできないようにする
4. 退会処理が成功したら、端末のログイン状態を解除し（ログアウト）、ログイン画面に移動して、完了ダイアログを表示する。ログアウトに失敗しても、サーバー側のユーザーは削除済みなので、成功として扱う

2. 本文「退会すると全てのデータが削除されます。それでも退会しますか？」

| 操作 | 処理 |
|-----|------|

## 退会処理の状態の記録

退会処理がどこまで進んだかを、端末内の専用のテーブルに記録する（同期用のキューとは別にする）。

| 状態 | 意味 |
|-----|------|
| 削除中 | 関数 `deleteAccount` を呼んだが、成功をまだ受け取っていない |
| サーバー削除済み | 関数の成功を受け取った。端末内のデータの削除がまだ終わっていない |
| （記録なし） | 退会処理をしていない、または退会処理がすべて終わった |

- 最終確認ダイアログで OK を押したら、関数を呼ぶ前に「削除中」を記録する
- 関数の成功を受け取ったら「サーバー削除済み」に変える
- 端末内のデータの削除と、記録の削除は、1つのトランザクションで行う（どちらかだけが終わる状態を作らない）
- 記録がある間は、そのユーザーのデータの同期（取得・送信）を行わない。削除したデータが同期で作り直されるのを防ぐため
- 「削除中」を記録したあと、実行中の同期が終わるのを待ってから関数を呼ぶ

## 途中で止まった場合

アプリを起動したとき（ログイン中かどうかに関わらない）に記録があれば、他の画面の上に「退会処理の再開ダイアログ」を表示する。退会を終えるまで、アプリの他の機能は使えない。

再試行を押下したときの処理は、記録の状態で決める。

| 記録の状態 | 再試行の処理 |
|-----------|------------|
| 削除中 | 関数 `deleteAccount` をもう一度呼ぶ。成功したら端末内のデータを削除する |
| 削除中（ログインしていない、またはログイン情報が無効と返された） | サーバー側で Authentication のユーザーまで削除が終わっているとみなし、関数は呼ばずに端末内のデータを削除する |
| サーバー削除済み | 関数は呼ばずに、端末内のデータを削除する |

## 操作が失敗したとき

| 失敗した場所 | 処理 |
|------------|------|
| 関数を呼ぶ前に通信できないと分かった、または関数に届かなかった（通信エラー） | 何も削除されていないので、記録を消し、同期を元に戻して、「退会できませんでした」ダイアログを表示する |
| 関数に届いたか分からない（応答が時間内に来ない、その他のエラー） | 記録を「削除中」のまま残し、「退会処理の再開ダイアログ」を表示する |
| 端末内のデータの削除に失敗した | 記録を「サーバー削除済み」のまま残し、「退会処理の再開ダイアログ」を表示する |

- 退会処理の失敗では、通信エラーでも、通信エラーダイアログの表示と強制ログアウトは行わない（共通原則-11 の例外）。退会処理の途中でログアウトすると、再開できなくなるため

## 退会済みの記録

他の端末で退会したことを、別の端末が知るための記録。

- 関数 `deleteAccount` が、Firestore の `deleted_accounts/{uid}` に退会した日時とメールアドレスを書き込む（ユーザー決定 2026-10-19）
  - メールアドレスは、退会後にトラブルがあったときに、規約への同意の履歴（`consent_logs/{uid}`）と本人を結びつけるために残す
  - メールアドレスは Firebase Authentication のユーザーから取る。メールアドレスの無いユーザーは書き込まない
  - Authentication のユーザーを削除した後の再試行でも、前回書いたメールアドレスは消さない
  - 記録はログインしていない端末からも1件ずつ読めるため、uid を知っていればメールアドレスも読める（ユーザー了承済み）
- 退会後も削除しない。Firebase Authentication の uid は別のユーザーに再利用されないため、uid で退会済みかどうかを判定できる
- 関数を何度呼んでも、記録は1つのまま（上書きする）
- 退会済みの記録がある uid の `users/{uid}` 配下への書き込みは、Firestore のルールで拒否する。他の端末に残っているログイン情報（最大1時間有効）で、同期によって削除したデータが作り直されるのを防ぐため
- 退会済みの記録は、ログインしていない端末からも1件ずつ読める（一覧は読めない）。書き込みはサーバーだけ
- この記録を導入する前に退会したユーザーは、記録が無いため「他の端末での退会」の対象外とする
- このルールは `@firebase/rules-unit-testing` と Firebase Emulator で自動テストする
- 退会後も uid・退会日時・メールアドレスを保持すること、他の端末のデータも削除されることは、利用規約・プライバシーポリシーに記載する（`legal_consent.md` §退会時）

## 他の端末での退会

ある端末（B）で退会したとき、同じアカウントを使っていた別の端末（A）に残っているデータを削除する。

### 確認のタイミング

- アプリの起動時と、アプリがフォアグラウンドに戻ったとき（resumed）に確認する
- ログイン中は、ログイン中の uid の退会済みの記録をリアルタイムで監視する。記録ができたら、どの画面を操作していても、すぐに「アカウント削除のお知らせダイアログ」を表示する
  - オフラインの間と、アプリがバックグラウンドにある間は監視できないため、起動時・resumed の確認で補う
  - 監視はログインしたときに始め、ログアウトしたときに止める
- 確認は裏で行い、起動時に確認の応答を待たない（スプラッシュ画面で待たせない）。退会済みと分かった時点で、ダイアログを表示する
- オフラインのときは確認しない。退会済みの記録を読めなかった uid も、次のきっかけでもう一度確認する
- 端末内にデータがある uid と、ログイン中の uid のすべてについて、退会済みの記録があるかを確認する（ログイン中かどうか、ログアウト済みかどうかに関わらない）
- 退会処理の記録がある間は確認しない（この端末で退会処理をしている途中なので、「途中で止まった場合」に従う）。退会処理が終わった後は、次のきっかけ（起動時・resumed）で確認する

### 退会済みが見つかったとき

ログイン中のアカウントが退会済みの場合:

1. 今の画面の上に「アカウント削除のお知らせダイアログ」を表示する。ほかのダイアログ（退会の確認ダイアログなど）を表示していれば、それを閉じてから表示する
2. OK を押下すると、ログアウトしてログイン画面に移動する。未送信の変更は送信しない（退会済みのため）
   - ログアウトに失敗したら、もう一度ログアウトする
   - それでも失敗したら、アプリとしてはログアウトしたものとして扱う（強制ログアウト）。ログイン画面に移動し、そのアカウントでは画面も同期も使えないようにする。アプリを起動し直しても同じように扱い、ログアウトは起動のたびにやり直す
3. ログイン画面に移動した直後に、「データの削除ダイアログ」を表示する
4. データの削除ダイアログで OK を押下すると、そのアカウントの端末内のデータをすべて削除する

ログアウト済みのアカウント（強制ログアウト済みを含む）が退会済みの場合:

1. 何も表示せずに、そのアカウントの端末内のデータをすべて削除する。ログイン中のアカウント（別のアカウントでログイン中の場合）の操作は妨げず、画面も移動しない
2. 削除に失敗しても何も表示せず、次のきっかけ（起動時・resumed）で削除をやり直す
   - 別のアカウントで操作中にダイアログを出すと、ログイン中のアカウントのデータが消えると誤解されるおそれがあるため、表示しない
   - 退会したユーザー本人が、退会時に「全てのデータが削除されます」に同意しているため、確認せずに削除する

どちらの場合も、削除するのは退会済みのアカウントの端末内のデータすべて（フォルダ・単語・学習結果・設定・未送信のキュー・同期の基準）で、同じ端末で使っている他のアカウントのデータは残す。

- 削除は、対象のアカウントすべてを1つのトランザクションで行う（すべて削除されるか、何も削除されないかのどちらか）
- データの削除ダイアログの OK を押下する前にアプリを終了した場合、次の起動時にはそのアカウントはログアウト済み（または強制ログアウト済み）なので、何も表示せずに削除する

2. 本文「このアカウントは他の端末で退会されたため、ログアウトします。引き続きご利用になる場合は、新しいアカウントで登録してログインしてください。」
3. OKボタン（ボタンはこれ1つだけ）

### データの削除ダイアログ

1. タイトル「データの削除」
2. 本文「このアカウントは他の端末で退会済みです。この端末に残っている WordPods のデータをすべて削除します。」
3. OKボタン（ボタンはこれ1つだけ）

| 操作 | 処理 |
|-----|------|
| OKを押下 | 端末内のデータを削除する。処理中は OK ボタンを押せないようにし、ダイアログの中にローディングを表示する |

2. 本文「端末内のデータを削除できませんでした。もう一度お試しください。」

| OKを押下 | ダイアログを閉じて、「データの削除ダイアログ」をもう一度表示する（OK で削除をやり直す） |
| ダイアログの外側をタップ・戻る操作 | 何もしない（ダイアログを閉じない） |

## 画面遷移

| 操作 | 遷移先 |
|-----|-------|
| 退会処理（再試行を含む）が成功 | ログイン画面（`/login`）。その上に完了ダイアログを表示する |
| 「退会できませんでした」ダイアログで OK | 設定画面のまま |
| アカウント削除のお知らせダイアログで OK を押下 | ログイン画面（`/login`）。その上にデータの削除ダイアログを表示する（ログアウトに失敗しても同じ） |
| データの削除ダイアログで OK を押下し、削除が成功 | 今の画面のまま |
