# メールアドレス確認 概要設計書

## 目的

- 新規登録したメールアドレスが、登録した本人のものであることを確かめる
- 存在しないメールアドレスや、他人のメールアドレスでは使い始められないようにする

## 方式

- Firebase Authentication 標準の確認メール（メール内のリンクを押す方式）を使う
- リンクを押すと、ブラウザで Firebase の確認完了ページが開き、そのアカウントが「確認済み」になる
- 確認メールは日本語で送る

### 今回やらないこと

| やらないこと | 理由 |
|------------|------|
| 番号（ワンタイムコード）を入力する方式 | Firebase に標準の機能がなく、自作の手間が大きい |
| SMS での確認 | 電話番号の確認の仕組みで、メールアドレスの確認には使えない |
| リンクから直接アプリを開く仕組み（ディープリンク） | 今回は、アプリに戻った時点で確認状態を問い合わせることで足りる |
| 確認完了ページを独自のデザインにする | 標準のページで足りる |
| 未確認のまま放置されたアカウントの自動削除 | 他人に先に登録された場合も、本来の持ち主はログイン画面の「パスワードを忘れた方」でパスワードを設定し直し、アカウントを取り戻せる（再設定のメールは持ち主に届く）。そのため急がない |

## アカウントの状態と表示する画面

| 状態 | 表示する画面 |
|-----|------------|
| 未ログイン | ログイン画面（今までどおり） |
| ログイン済み・未確認 | 確認待ち画面（`/verify-email`）。ほかの画面には移れない |
| ログイン済み・確認済み | ホーム画面など（今までどおり） |

- Firebase では、新規登録した時点でログイン済みになる。確認待ち画面にいる間も「ログイン済み・未確認」の状態
- Google でログインしたユーザーは、最初から確認済みとして扱われる（Google がメールアドレスを確認済みのため）。今までどおり確認待ち画面は表示しない
- 確認済みになったら、ログインし直さずにそのままホーム画面へ移る

## 新規登録

1. 新規登録画面で「アカウント作成」を押下する（画面の構成は今までどおり）
2. アカウントを作成する
3. 利用規約・プライバシーポリシーへの同意を送信する（今までどおり。`legal_consent.md`）
4. 確認メールを送信する
5. 新規登録画面の上に「確認メールの送信完了ダイアログ」を表示する
6. ダイアログを閉じたら、確認状態を問い合わせ、確認済みならホーム画面、未確認なら確認待ち画面へ移る

- 今までは登録の直後に同期してホーム画面へ移っていたが、登録の直後は同期せず、ホーム画面へも移らない
- 確認メールの送信に失敗しても、アカウントは作成済みのため、登録は成功として扱う（確認待ち画面の「確認メールを再送」で送り直せる）
- アカウントの作成に失敗した場合は、今までどおり新規登録画面にエラーを表示し、ダイアログは表示しない

### 確認メールの送信完了ダイアログ

確認メールの送信に成功した場合:

1. タイトル「確認メールを送信しました」
2. 本文「（登録したメールアドレス）に本人確認用のメールを送信しました。メール内のリンクを押して、登録を完了してください。」
3. ボタン「閉じる」だけ

確認メールの送信に失敗した場合:

1. タイトル「アカウントを作成しました」
2. 本文「確認メールを送信できませんでした。次の画面の「確認メールを再送」から、もう一度送信してください。」
3. ボタン「閉じる」だけ

- どちらも「閉じる」でだけ閉じる。ダイアログの外側の押下・戻る操作では閉じない（閉じた後の移動先を必ず通すため）
- ダイアログを表示している間は、確認状態が変わっても画面を移らない
- ダイアログを開いたままメールのリンクを押してアプリに戻り、その後「閉じる」を押下した場合は、確認待ち画面を経由せずにホーム画面へ移る（ユーザー決定 2026-11-07）
- 「閉じる」の後の確認状態の問い合わせに失敗しても、何も表示せずに確認待ち画面へ移る（確認待ち画面で、もう一度問い合わせられるため）

## 確認待ち画面

### 画面への入り方

- 新規登録の後、送信完了ダイアログを閉じたときに未確認だった場合
- 未確認のアカウントでログインした場合
- 未確認のアカウントでログインしたままアプリを起動した場合
- ボトムナビゲーションバーは表示しない。戻るボタンは表示しない

### 画面構成

- AppBar には「メールアドレスの確認」と表示する
- AppBar の右上に「ログイン画面へ」ボタンを置く（ユーザー決定 2026-11-07）
- 本文
  - 「（ログイン中のメールアドレス）に確認メールを送信しました。メール内のリンクを押して、登録を完了してください。」
  - 「メールが届かない場合は、迷惑メールフォルダもご確認ください。」
- 本文の下に、上から「確認しました」「確認メールを再送」の順にボタンを置く

### 確認しました

- 押下すると、確認状態を問い合わせる
- 確認済みなら、ホーム画面へ移る
- 未確認なら、スナックバーに「まだ確認が完了していません。メール内のリンクを押してください。」と表示する
- 問い合わせている間は、ボタンを押せないようにし、処理中であることを表示する

### 確認メールを再送

- 押下すると、確認メールを送信する
- 送信に成功したら、スナックバーに「確認メールを再送しました」と表示する
- 確認メールの送信に成功してから60秒間は押せない。押せない間は、ボタンに残りの秒数を「確認メールを再送（あと◯秒）」と表示する
- 60秒は、新規登録のときの送信からも数える（登録の直後に再送を連打させないため）
- 送信している間は、ボタンを押せないようにし、処理中であることを表示する

### ログイン画面へ

- 押下すると、ログアウトしてログイン画面へ移る（ログイン済みのままでは、すぐ確認待ち画面に戻されるため）
- メールアドレスを打ち間違えたユーザーが、別のメールアドレスで登録し直すための入り口になる
- 確認ダイアログは挟まない（ログアウトしても、同じメールアドレスとパスワードでログインし直せるため）

### 自動の確認

次のときにも、確認状態を問い合わせる。確認済みならホーム画面へ移る。

| タイミング | 目的 |
|----------|------|
| 確認待ち画面を表示したとき | リンクを押した後にアプリを起動し直した場合に、すぐホーム画面へ移す |
| アプリが前面に戻ったとき | リンクを押した後、そのままアプリに戻った場合に、ホーム画面へ移す |

- 自動の確認では、未確認だった場合も、問い合わせに失敗した場合も、何も表示しない（ユーザーが操作していないため）
- ただし、アカウントが無い等でログアウトしようとして、そのログアウトにも失敗した場合は、「ログアウトに失敗しました。時間をおいて再度お試しください。」と表示する（ログイン画面に戻れず、操作できない状態になるため）

### エラーの扱い

「確認しました」「確認メールを再送」の失敗は、次のようにスナックバーで伝える。

| エラー | 表示・動作 |
|------|-----------|
| 通信エラー | 「通信エラーが発生しました。電波の良い場所で再度お試しください。」と表示する。**ログアウトしない**（ユーザー決定 2026-11-07。全画面共通の「通信エラーでログアウトする」原則の例外。圏外で押しただけでログアウトされないようにするため） |
| 短時間に何度も送信した | 「短時間に何度も送信されました。しばらく時間をおいてから再度お試しください。」と表示する |
| アカウントが無い・無効にされた・ログイン情報の期限切れ | ログアウトしてログイン画面へ移る（自動の確認で起きた場合も同じ） |
| そのほか | 「エラーが発生しました。時間をおいて再度お試しください。」と表示する |

## ログイン

- ログインの操作は今までどおり。未確認のアカウントでもログイン自体はできる
- ログインした後、未確認なら確認待ち画面へ、確認済みならホーム画面へ移る
- 未確認の場合は、ログインの直後に同期しない

## アプリの起動

- 起動時に、確認状態の問い合わせを待たない（電波の弱い場所で起動が遅くならないようにするため）
- 端末に保存されたログイン情報が未確認なら、確認待ち画面を表示する。表示したときの自動の確認で確認済みと分かれば、ホーム画面へ移る
- 一度確認済みになれば、その状態は端末に保存される。オフラインでもホーム画面に入れる

## 同期

- 未確認の間は、同期（取得・送信とも）を行わない（未確認のユーザーは Firestore を読み書きできないため。下記「Firestore のルール」）
- 確認済みになった時点で、ログインしたときと同じ同期を始める
- 確認済みになったときは、Firestore への読み書きに使うログイン情報も確認済みのものに更新してから同期する（古いログイン情報のままだと、確認済みでも読み書きを断られるため）

## Firestore のルール

- アプリの画面の振り分けを通らずに直接アクセスされても、データを守れるようにする
- ユーザーのデータ（`users/{uid}` 配下のフォルダ・単語・テスト結果・設定）の読み書きに、「確認済みであること」を条件として加える
- 次は変えない
  - `accounts/{uid}`（開発者フラグ・規約への同意）: 本人は読むだけで、書き込みはサーバーだけのため。未確認の間に読めても困らず、規約への同意の判定もそのまま動く
  - `app_config`（規約の版数）・`deleted_accounts`: ログインしていない状態でも読む必要があるため
  - Cloud Functions（同意の送信・退会・新規登録時の `accounts` 作成）: サーバーの権限で書き込むため、ルールの影響を受けない
- ルールの変更に合わせて、ルールのテストも更新する

## 既存のユーザー

- この機能を入れる前にメールアドレスとパスワードで登録したユーザーは、未確認のまま残っている
- 一括で確認済みにする移行の処理は行わない。既存ユーザーも新規ユーザーと同じく、ログイン後の確認待ち画面で確認メールを再送し、リンクを押して確認する（ユーザー決定 2026-11-07。現在の利用者は開発者1名のため）
- 確認が済むまでは同期が止まるだけで、データは消えない。確認後に同期が再開する

## Mock モード（`USE_MOCKS=true`）

- 開発用のユーザーは最初から確認済みとして扱い、今までどおりすぐホーム画面に入れる
- 確認メールの送信・確認状態の問い合わせは、Mock では成功を返す

## Firebase コンソールでの設定（手作業。開発・本番の両方のプロジェクトで行う）

- Authentication → テンプレート → 「メールアドレスの確認」で、テンプレートの言語を日本語にし、送信者名・件名・本文をアプリ名に合わせて変更する

## 画面遷移

| 画面 | 操作・状態 | 遷移先 |
|-----|----------|-------|
| 新規登録画面 | 送信完了ダイアログの「閉じる」を押下し、確認済みだった | ホーム画面（`/home`） |
| 新規登録画面 | 送信完了ダイアログの「閉じる」を押下し、未確認だった | 確認待ち画面（`/verify-email`） |
| ログイン画面 | 未確認のアカウントでログインした | 確認待ち画面（`/verify-email`） |
| スプラッシュ画面 | 未確認のアカウントでログイン済みのまま起動した | 確認待ち画面（`/verify-email`） |
| 確認待ち画面 | 「確認しました」・自動の確認で確認済みと分かった | ホーム画面（`/home`） |
| 確認待ち画面 | 「ログイン画面へ」を押下した | ログイン画面（`/login`） |
| 確認待ち画面 | 問い合わせで、アカウントが無い・無効・ログイン情報の期限切れと分かった | ログイン画面（`/login`） |
| （どの画面でも） | ログイン済み・未確認で、確認待ち画面以外を開こうとした | 確認待ち画面（`/verify-email`） |
| 確認待ち画面 | ログイン済み・確認済みで開こうとした | ホーム画面（`/home`） |
