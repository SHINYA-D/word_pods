# 利用規約・プライバシーポリシーへの同意 概要設計書

## 目的

ユーザーが利用規約とプライバシーポリシーに同意したことを、いつ・どの版に同意したかが分かる形で記録する。
同意していない（または改定後の版に同意していない）ユーザーには、同意するまでアプリを使わせない（ユーザー決定 2026-10-18「同意していないと利用できない」）。

- 新規登録は、新規登録画面で両方の文書に同意しないとできない（§新規登録）
- 登録済みのユーザーは、規約が改定されるたびに同意ダイアログで同意し直す。同意の記録が無いユーザー（この機能より前に登録したユーザーを含む）にも同意ダイアログを出す

## 対象の文書

- 利用規約
- プライバシーポリシー
- 本文は WEB で公開する。アプリは本文を持たず、WEB のページを WebView で表示する（WEB と同じ文言を保つため）
- 公開 URL は `app_config/legal` の `termsUrl` / `privacyUrl` に置く（ユーザー決定 2026-10-15）
  - 利用規約: `https://word-pods-web.web.app/terms`
  - プライバシーポリシー: `https://word-pods-web.web.app/privacy`

## 版数の管理

- 現行の版数と URL は `app_config/legal` に置く（`termsVersion` / `privacyVersion` / `termsUrl` / `privacyUrl`。データ構造は `requirements.md` §8）
- 誰でも読める（ログイン前でも読めるルールのまま）。書き込みはコンソールなどサーバー側だけ
- 版数は改定日を `YYYY-MM-DD` の文字列で書く（例: `2026-01-01`）
- 版数は文字列が一致するかだけで比べる（日付の新旧は比べない）

### 既定値

`app_config/legal` が無い、または4項目のどれかが無い（空・文字列でない）ときは、既定値を現行の版数・URL として使う（ユーザー決定 2026-10-18。設定データが無いことで同意を素通りさせないため）。

| 項目 | 既定値 |
|-----|-------|
| `termsVersion` | `2026-10-12`（WEB の利用規約の最終更新日） |
| `privacyVersion` | `2026-10-12`（WEB のプライバシーポリシーの最終更新日） |
| `termsUrl` | `https://word-pods-web.web.app/terms` |
| `privacyUrl` | `https://word-pods-web.web.app/privacy` |

- 項目の一部だけが欠けているときも、4項目すべてを既定値に置き換える（欠けた項目だけを補うと、版数と URL の組み合わせが食い違うおそれがあるため）
- 既定値は、アプリと関数 `acceptLegal` の両方に同じ値で持つ
- 関数 `acceptLegal` は、`app_config/legal` が無ければ、同意を記録するときに既定値で作る（すでにあれば書き換えない）。最初に誰かが同意した時点で、`app_config/legal` がそろう
- `app_config/legal` はあるが項目が欠けているときは、関数も既定値で版数を確かめる（アプリと同じ扱いにして、版数違いが返り続けないようにする）。ドキュメントは書き換えない
- 規約を改定したら、`app_config/legal` を書き換える（下記「改定するときの運用」）。次のリリースで、アプリと関数の既定値も同じ値に揃える

### 改定するときの運用

1. WEB の文面と改定日を更新する
2. Firestore コンソールで `app_config/legal` の版数を、WEB の改定日と同じ日付に書き換える
3. 次のリリースで、アプリと関数の既定値（§既定値）も同じ値に揃える
- 誤字の修正など、同意し直してもらう必要がない変更は、WEB だけを直して版数は変えない
- 利用規約とプライバシーポリシーの版数は別々に変える。片方だけ改定したら、その片方の版数だけを変える

## 同意が必要かの判定

ログイン中のユーザーについて、`app_config/legal` の現行の版数（無ければ既定値）と、`accounts/{uid}.consents` の同意済みの版数を、文書ごとに比べる。

| 状態 | その文書への同意 |
|-----|----------------|
| 同意済みの版数が現行の版数と一致する | 不要 |
| 同意済みの版数が現行の版数と違う | 必要 |
| 同意の記録が無い（`accounts/{uid}` やその `consents`、その文書のフィールドが無い） | 必要 |

- 新規登録画面で同意して登録した直後は、同意が記録されているので不要になる（§新規登録）。記録に失敗していれば必要になる
- どちらか一方でも同意が必要なら、同意ダイアログを表示する

### 判定のタイミング

- ログインしたとき（新規登録・メール・Google のどれでも）
- アプリの起動時（ログイン済みのとき）
- アプリがフォアグラウンドに戻ったとき（resumed）。起動中に規約を改定した場合に備えるため
- オフラインからオンラインに戻ったとき（ユーザー決定 2026-10-18。オフラインの間は出さず、オンラインになった時点で出すため）
- ログイン直後は、ログインの処理（新規登録では同意の送信を含む）と初回の同期が終わってから判定する（新規登録画面での同意の記録が終わる前に判定して、同意ダイアログを誤って出さないため）。同期が失敗しても、終わった時点で判定する
- オンラインに戻ったときも、ほかのきっかけと同じく、判定しないとき（ログインしていない・ダイアログの表示中・退会関係のダイアログの表示中など）は判定しない
- 判定はサーバーの最新の値で行う（端末に残っている前回の値で判定しない）
- 判定は裏で行い、結果を待たずに画面を表示する。同意が必要と分かった時点で、同意ダイアログを表示する

### 判定しないとき・判定できないとき

- ログインしていないときは判定しない（他の端末での退会で強制ログアウトした uid も、ログインしていないものとして扱う）
- オフラインのときは判定せず、同意ダイアログを出さない。オンラインに戻ったとき（またはほかのきっかけ）でもう一度判定する（ユーザー決定 2026-10-14・2026-10-18）
- 読み取りに失敗したとき（通信できない以外の失敗）は、同意ダイアログを出さない。次のきっかけでもう一度判定する
- `app_config/legal` や現行の版数が無いときは、既定値で判定する（§既定値）。同意ダイアログを出さずに素通りさせない（ユーザー決定 2026-10-18）
- 同意ダイアログを表示している間は、判定し直さない（ダイアログを2つ重ねない・チェックの状態を消さない）

### ほかのダイアログとの優先順位

退会関係のダイアログを優先し、それらを表示している間は同意ダイアログを表示しない。

1. 退会処理の再開ダイアログ（`presentation/settings/high_settings_page.md` §途中で止まった場合）
2. 他の端末での退会のダイアログ（同 §他の端末での退会）
3. 同意ダイアログ

- 退会処理の記録がある間は、判定しない。退会では `accounts/{uid}` が先に削除されるため、判定すると「同意の記録が無い」と誤って判定してしまう
- 同意ダイアログを表示している間に他の端末での退会が分かったら、同意ダイアログを閉じて、お知らせダイアログを表示する
- ログアウトしたら（どの理由でも）、同意ダイアログを閉じる

## 同意ダイアログ

同意が必要と分かったら、今の画面の上に表示する。スプラッシュ画面の間は、移動先の画面が決まってから表示する。

1. タイトル「同意のお願い」
2. 本文「WordPods を利用するには、次の内容への同意が必要です。リンクから内容を確認し、チェックを入れてください。」
3. 利用規約の行: リンク「利用規約を読む」、チェックボックス「利用規約に同意する」
4. プライバシーポリシーの行: リンク「プライバシーポリシーを読む」、チェックボックス「プライバシーポリシーに同意する」
5. 「同意する」ボタン
6. 「ログアウト」ボタン（テキストのボタン）

- 同意が必要な文書の行だけを表示する。片方だけ改定したときは、その片方の行だけになる（ユーザー決定 2026-10-14）
- チェックボックスは、最初はすべて未チェック
- 表示しているチェックボックスがすべてチェックされるまで、「同意する」ボタンは押せない（ユーザー決定 2026-10-14）
- リンクを開かなくてもチェックできる（ユーザー決定 2026-10-14。開いたかどうかは読んだことの証明にならないため）
- 画面に収まらないときは、ダイアログの中をスクロールできる
- 「同意しない」「キャンセル」のボタンは置かない
- 同意するまでアプリの他の機能は使えない（ユーザー決定 2026-10-14）
- 「ログアウト」ボタンを置く（ユーザー決定 2026-10-14）。同意したくないユーザーや、別のアカウントに切り替えたいユーザーの逃げ道にするため
- 別のダイアログ（フォルダの作成など）が開いている画面で同意が必要と分かったときは、そのダイアログの上に重ねて表示する。下のダイアログと入力内容はそのまま残し、同意した後に戻れるようにする（ユーザー決定 2026-10-14）

| 操作 | 処理 |
|-----|------|
| リンクを押下 | その文書の閲覧画面を開く（下記「規約の閲覧画面」） |
| チェックボックス（または文言）を押下 | チェックを付ける・外す |
| 「同意する」を押下 | 同意を送信する（下記「同意の送信」） |
| 「ログアウト」を押下 | ログアウトしてログイン画面に移動する（確認のダイアログは出さない。取り消せない操作ではないため）。送信中は押せない |
| ログアウトに失敗 | 同意ダイアログを閉じずに、「ログアウトできませんでした。もう一度お試しください。」を表示する。失敗の種類は区別しない（通信エラーでも通信エラーダイアログは出さない。ログアウトの失敗でログアウトを促すことになるため） |
| ダイアログの外側をタップ・戻る操作 | 何もしない（ダイアログを閉じない） |

## 規約の閲覧画面

同意ダイアログのリンクから開く、全画面の WebView の画面。ダイアログの上に重ねて開く（ユーザー決定 2026-10-14）。

1. 上部のバーに、文書の名前（「利用規約」または「プライバシーポリシー」）と戻るボタン
2. 本文の領域に、その文書の URL（`termsUrl` / `privacyUrl`）のページを表示する

| 操作・状態 | 処理 |
|-----|------|
| 読み込み中 | ローディングを表示する |
| 読み込みに失敗（オフライン等） | 「ページを読み込めませんでした。通信環境を確認して、もう一度お試しください。」と「再読み込み」ボタンを表示する |
| 「再読み込み」を押下 | もう一度読み込む |
| 戻るボタン・戻る操作 | 閲覧画面を閉じて、同意ダイアログに戻る。チェックの状態はそのまま |

- 閲覧画面での読み込みの失敗では、通信エラーダイアログの表示と強制ログアウトは行わない（閲覧しているだけで、送信していないため）

## 同意の送信

- 「同意する」を押下すると、Cloud Functions の関数（callable、`acceptLegal`）を呼ぶ。送るのは、ダイアログに表示した文書とその版数
- 送信中は「同意する」ボタン・チェックボックス・リンクを押せないようにし、ダイアログの中にローディングを表示する
- 関数は、呼び出したユーザーの uid（`request.auth.uid`）で記録する（下記「同意の記録」）

| 結果 | 処理 |
|-----|------|
| 成功 | 同意ダイアログを閉じる。今の画面のまま使えるようになる |
| 送った版数が現行の版数と違う（表示中に改定された） | 同意ダイアログを閉じずに、判定し直した結果で表示し直す。チェックはすべて外し、「内容が更新されました。もう一度ご確認のうえ、同意してください。」を表示する |
| 通信エラー・認証エラー | 同意ダイアログを閉じて、通信エラーダイアログを表示し、OK でログアウトしてログイン画面に移動する（共通原則-11。ユーザー決定 2026-10-14）。再ログインしたときの判定で、同意ダイアログがもう一度表示される |
| その他のエラー | 同意ダイアログを閉じずに、チェックの状態はそのままで、「同意を送信できませんでした。もう一度お試しください。」を表示する。もう一度「同意する」を押せる |

- 通信エラーダイアログの OK でログアウトに失敗したときは、判定し直し、同意が必要なら同意ダイアログを出し直す（チェックはすべて外れる）。同意しないまま使える状態を作らないため（ユーザー決定 2026-10-14）
- 通信エラーダイアログを表示している間に他の端末での退会が分かったときは、通信エラーダイアログを閉じて、お知らせダイアログを表示する（`presentation/settings/high_settings_page.md` §退会済みが見つかったとき「ほかのダイアログを表示していれば、それを閉じてから表示する」に従う）
- 「内容が更新されました。…」「同意を送信できませんでした。…」「ログアウトできませんでした。…」の文言は、次に「同意する」または「ログアウト」を押したときに消える。チェックを切り替えても消えない（ユーザー決定 2026-10-14）

## 同意の記録

関数 `acceptLegal` が、次の2つを1つのバッチで書き込む。時刻はサーバー時刻（`agreedAt`）にする（端末時刻ではなく、証跡として改ざんできないようにするため）。

| 記録 | 場所 | 内容 | 用途 |
|-----|------|------|------|
| 最新の同意 | `accounts/{uid}.consents` | 文書ごとに、同意した版数と日時（上書き） | 同意が必要かの判定 |
| 同意の履歴 | `consent_logs/{uid}/logs/{自動ID}` | 同意した文書（`terms` / `privacy`）・版数・日時（追記。同意した文書ごとに1件） | 証跡（ユーザー決定 2026-10-14） |

- 関数は、送られた版数が `app_config/legal` の現行の版数と一致するかを確かめる。一致しなければ何も書き込まず、「版数が違う」と返す
- `app_config/legal` が無いときは、関数が既定値（§既定値）で作ってから確かめる。すでにあれば書き換えない（コンソールで書き換えた値を上書きしないため）
- `accounts/{uid}` には `set(..., { merge: true })` で `consents` だけを書き、他のフィールドを壊さない
  - 新規登録の直後で `accounts/{uid}` がまだ作られていない場合は、関数が `consents` と一緒に `isDeveloper: false` と `createdAt` も書く。すでにあるフィールドは上書きしない（`requirements.md` §8 の常にそろえるフィールド。ユーザー決定 2026-10-19）
- 同意の履歴は `accounts` とは別のトップレベルのコレクションに置く。`accounts/{uid}` は退会で削除されるが、履歴は退会後も残すため
- クライアントは `accounts` にも `consent_logs` にも書き込まない。`consent_logs` は読むこともできない（Firestore のルールで禁止する）
- 同じ版数で何度呼んでも、最新の同意は同じ内容になる（履歴は呼んだ回数だけ増える）

## 新規登録

新規登録画面で両方の文書に同意しないと、アカウントを作れない（ユーザー決定 2026-10-18）。

### 新規登録画面の構成

「パスワード（確認）」の下、「アカウント作成」ボタンの上に、次を置く。

1. 利用規約の行: リンク「利用規約を読む」、チェックボックス「利用規約に同意する」
2. プライバシーポリシーの行: リンク「プライバシーポリシーを読む」、チェックボックス「プライバシーポリシーに同意する」

- 表示や文言は同意ダイアログの行と同じ。チェックボックスは最初は未チェック。文言を押下してもチェックが切り替わる
- 2つともチェックされるまで、「アカウント作成」ボタンは押せない（ユーザー決定 2026-10-18）
- 新規登録画面を開いたときに `app_config/legal` を読み、リンクの URL と、送る版数に使う。読めなかったとき（`app_config/legal` が無い・オフライン・読み取りの失敗）は既定値（§既定値）を使う
- 読み込んでいる間は「アカウント作成」ボタンとリンクを押せない（読み込みは短く、終わればすぐ押せるようになるため、ローディングは表示しない）
- リンクを押下すると、同意ダイアログのリンクと同じ閲覧画面を開く。戻ると新規登録画面に戻り、入力内容とチェックの状態はそのまま

### 登録の流れ

1. 2つともチェックして「アカウント作成」を押下する（メールアドレスなどの入力チェックは今までどおり）
2. アカウントを作る
3. アカウントができたら（uid が決まったら）、画面に表示した版数で、同意を自動で送信する（関数 `acceptLegal`。同意ダイアログの「同意する」と同じ記録）
4. 初回の同期が終わったらホーム画面に移る。同意の判定はこの後に行う（§判定のタイミング）
- 同意の送信の応答が来ないときは、時間切れ（30秒）で失敗として扱い、先に進む

| 結果 | 処理 |
|-----|------|
| アカウントの作成が失敗（失敗の種類によらない） | 今までどおりエラーをスナックバーで表示する。同意は送信しない。入力内容とチェックの状態はそのまま |
| 同意の送信が成功 | ホーム画面に移る。同意ダイアログは出ない |
| 同意の送信が失敗（通信エラー・認証エラーを含め、失敗の種類によらない）・版数が違う | エラーは表示せず（通信エラーダイアログ・強制ログアウトもしない。アカウントはできていて、後の判定で同意を求められるため）、ホーム画面に移る。その後の判定で同意の記録が無いと分かり、同意ダイアログが出る（アカウントはできているが、同意するまでアプリは使えない） |

### Google で新規登録する場合

- Google のアカウントでの新規登録は、ログイン画面の「Google でログイン」から行う（新規か既存かは、ログインするまで分からない）
- 新規登録画面を通らないため、ログイン後の判定で同意ダイアログを出す（アカウントはできるが、同意するまでアプリは使えない）（ユーザー決定 2026-10-18。既存のユーザーにログインのたびのチェックを求めないため）

## 退会時

- 退会すると、`accounts/{uid}` と一緒に最新の同意（`consents`）は削除される
- 同意の履歴（`consent_logs/{uid}`）は退会後も削除せず、uid と一緒に残す（ユーザー決定 2026-10-14）。保持期間は定めない
  - 履歴は uid・文書・版数・日時だけで、メールアドレスなどの個人を特定できる情報は持たない
  - 退会の関数 `deleteAccount` は `users/{uid}` と `accounts/{uid}` だけを削除するので、変更しなくても履歴は残る
- 利用規約・プライバシーポリシーの本文（WEB）には、退会について次の事項を必ず記載する（ユーザー決定 2026-10-12・2026-10-14。退会の仕様は `presentation/settings/high_settings_page.md`）
  - 退会すると、他の端末に残っているデータも、その端末でアプリを起動したときに削除される
  - 退会後も、退会済みであることの判定のために、アカウントの識別子（uid）と退会日時を保持する
  - 退会後も、規約への同意の記録（uid・同意した文書・版数・日時）を保持する
  - 退会後も、トラブルがあったときに同意の記録と本人を結びつけるために、メールアドレスを保持する（ユーザー決定 2026-10-19）

## 設定画面から規約を読む

同意した後も規約を読み返せるようにする（ユーザー決定 2026-10-14。App Store の審査はアプリ内からプライバシーポリシーを見られることを求めるため）。

- 設定画面の「外観」と「アカウント」の間に、見出し「このアプリについて」と、項目「利用規約」「プライバシーポリシー」を置く
- 項目を押下すると、`app_config/legal` から URL を読み、同意ダイアログのリンクと同じ閲覧画面を開く。戻ると設定画面に戻る
- `app_config/legal` や URL が無いときは、既定値（§既定値）の URL で閲覧画面を開く（ユーザー決定 2026-10-18）
- URL を読めなかったとき（オフライン・読み取りの失敗）は、閲覧画面を開かずに、スナックバーで「ページを開けませんでした。通信環境を確認して、もう一度お試しください。」を表示する。通信エラーダイアログの表示と強制ログアウトは行わない（読んでいるだけで、送信していないため）
- URL を読んでいる間に、もう一度押下しても、閲覧画面は1つだけ開く
- URL を読んでいる間は、押下した項目にローディングを表示する
- 閲覧画面を開いている間に同意が必要と分かったときは、閲覧画面の上に同意ダイアログを表示する（閲覧画面も「今の画面」として扱う）

## テスト

- 関数 `acceptLegal`（版数の確認・2つの記録の書き込み）は、Cloud Functions 側で Firebase Emulator を使って自動テストする
- `consent_logs` をクライアントが読み書きできないことは、`@firebase/rules-unit-testing` と Firebase Emulator で自動テストする
