# クラッシュ検知・Slack 通知・利用状況の分析 概要設計書

## 目的

- 利用者の端末でアプリが異常終了（クラッシュ）したことを、開発者が気づけるようにする
- どの端末・どのバージョン・コードのどこで落ちたかを調べられるようにする
- 新しいクラッシュ・再発・急増を、Slack で日本語で知らせる
- 落ちてはいないが想定外のエラー（非致命的エラー）にも気づけるようにする
- アプリがどう使われているか（利用者数・よく見られる画面）を知り、改善に役立てる

## 方式

| 部品 | 役割 |
|-----|------|
| Firebase Crashlytics | アプリのクラッシュ情報を集め、同じ原因のクラッシュを1つの「問題（issue）」にまとめる |
| Firebase Alerts | Crashlytics が「新しい問題」「再発」「急増」と判定したときに、イベントを出す |
| Cloud Functions | イベントを受けて、日本語の文面を作り、Slack に送る |
| Slack（Incoming Webhook） | 通知用チャンネルに投稿する |
| Firebase Analytics | 利用状況（起動・利用時間・見た画面）を集める。Crashlytics の画面に「クラッシュしなかった利用者の割合」や「落ちる直前に見ていた画面」も出るようになる |

- アプリは Crashlytics に送るだけで、Cloud Functions を直接呼ばない
- Firebase コンソール標準の Slack 連携は使わない（文面を日本語にし、開発・本番を分けて送るため。ユーザー決定 2026-11-08）

### 全体の流れ

1. アプリがクラッシュする。Crashlytics がクラッシュ情報を端末に保存する
2. 次にアプリを起動したときに、Crashlytics に送る
3. Crashlytics が問題にまとめ、新しい問題・再発・急増と判定したらアラートを出す
4. アラートで Cloud Functions の関数が起動し、Slack に投稿する

- 1回のクラッシュごとに通知するのではない。同じ原因のクラッシュは1つの問題にまとめられ、通知は「新しい問題」「再発」「急増」のときだけ届く
- クラッシュしてから通知が届くまでには、利用者が次に起動するまでの遅れがある

### 今回やらないこと

| やらないこと | 理由 |
|------------|------|
| PagerDuty などによる当番への呼び出し | 夜間に対応する体制がないため |
| Slack でのメンション（@ 付きの呼び出し） | 通知用チャンネルを見れば足りるため |
| Jira などへの自動起票 | 課題管理ツールを使っていないため |
| Google Play での配布向けの申告 | Google Play では現在リリースしていないため |
| プライバシーポリシーの本文の修正 | このブランチでは行わない（ユーザー決定 2026-11-08）。別の作業で行う |

- Firebase Analytics（利用状況の分析）は今回入れる（ユーザー決定 2026-11-08）。集める内容は「利用状況（Firebase Analytics）」の節
- 落ちていない想定外のエラー（非致命的エラー）も今回送る（ユーザー決定 2026-11-08）。送る範囲は「非致命的エラー（落ちていない想定外のエラー）」の節

## アプリ側

### クラッシュ情報を集めるとき・集めないとき

| ビルド | 集めるか | 理由 |
|-------|--------|------|
| リリースビルド（`--release`） | 集める | 利用者の端末で起きたクラッシュを知るため |
| デバッグビルド | 集めない | 開発中のエラーで通知が鳴らないようにするため。エラーは今までどおりコンソールに出す |
| Mock モード（`USE_MOCKS=true`） | 集めない | Firebase を使わずに動かすモードのため |

- 開発（`--flavor dev`）のリリースビルドで起きたクラッシュは、開発の Firebase プロジェクトに集まる。本番（`--flavor prod`）は本番のプロジェクトに集まる

### 集めるもの

| 種類 | 内容 |
|-----|------|
| 画面の描画などで起きたエラー | Flutter の処理中に起きて、どこでも受け止められなかったエラー。クラッシュとして記録する |
| それ以外の受け止められなかったエラー | 非同期の処理などで起きて、どこでも受け止められなかったエラー。クラッシュとして記録する |
| ネイティブのクラッシュ | iOS・Android の層での異常終了。Crashlytics が自動で集める |
| 誰のクラッシュか | ログイン中のユーザーの uid。ログアウトしたら外す |

- メールアドレス・表示名・単語などの入力内容は送らない
- 端末の機種・OS のバージョン・アプリのバージョンは Crashlytics が自動で付ける

### 非致命的エラー（落ちていない想定外のエラー）

アプリは落ちていないが、原因の分からないエラーを Crashlytics に「非致命的エラー」として送る（ユーザー決定 2026-11-08）。

| エラー | 送るか | 理由 |
|-------|-------|------|
| Repository で `UnknownFailure` になったエラー | 送る | 原因の分からないエラーで、開発者が知るべきもの。例外がきっかけでないもの（スタックトレースが無いもの）は送らない（ユーザー決定 2026-11-08） |
| `NetworkFailure`（通信エラー）・`AuthFailure`（ログイン切れ）・`NotFoundFailure`（データが見つからない） | 送らない | 圏外などで日常的に起きる想定内のエラーで、送ると通知が埋もれる |
| 裏で動く同期処理の失敗のうち、通信に関するもの以外 | 送る | 利用者の画面に出ないので、送らないと誰も気づけない |
| 裏で動く同期処理の失敗のうち、通信に関するもの（時間切れ・接続できない・Firestore が一時的に使えない）、ログイン切れ、混雑や中断による一時的な失敗 | 送らない | 想定内のエラーで、次の同期でやり直されるため（ユーザー決定 2026-11-08） |

- 送るのはエラーの内容とスタックトレース。集めるとき・集めないときは、クラッシュと同じ（デバッグビルド・Mock モードでは集めない）
- Repository の実装と同期処理には、報告用のインターフェースを Provider 経由で渡す

### 利用状況（Firebase Analytics）

利用状況を集める（ユーザー決定 2026-11-08）。

| 項目 | 集めるか | 理由 |
|-----|--------|------|
| 起動・利用時間など、Analytics が自動で集めるもの | 集める | 設定なしで集まる基本の数値 |
| 見た画面 | 集める | 画面が変わるたびに記録する。画面の名前はルートのパスの形（例: `/folder/:folderId`）にし、フォルダの ID などの値は入れない |
| 「単語を追加した」などの独自の操作 | 今回は集めない | 何を測りたいかが決まってから足す |
| 広告 ID | 集めない | 広告を出していないため。Android・iOS とも、広告 ID を集めない設定にする |
| uid | 付けない | 1人ずつの行動を追う必要がなく、Crashlytics 側の uid で足りる |

- 集めるとき・集めないときは、クラッシュと同じ（デバッグビルド・Mock モードでは集めない）
- ダイアログ・ボトムシートは画面として記録しない（ルートが変わらないため）
- Analytics への記録も、`domain` に置いた報告用のインターフェースを通して行い、テストでは Fake に差し替える

### 設計上の決まり

- Crashlytics への報告は、`domain` に置いた報告用のインターフェースを通して行う。Crashlytics を使った実装は `infrastructure` に置き、Provider 経由で渡す（CLAUDE.md のレイヤーと DI のルール）
- テストでは、報告用のインターフェースを手書きの Fake に差し替え、「何を何回報告したか」で確かめる

### ネイティブの設定

| 対象 | 設定 | 理由 |
|-----|------|------|
| Android | Crashlytics の Gradle プラグインを追加する | ネイティブのクラッシュを集めるため |
| iOS | `firebase.json` の `uploadDebugSymbols` を、Release 系の構成（`Release-dev`・`Release-prod`）で `true` にする | iOS のクラッシュの発生箇所を、関数名と行で読めるようにするため（読めないと、意味の分からない番地だけが届く） |

- Dart のコードの難読化（`--obfuscate`）は使っていないので、Dart 用のシンボルのアップロードは要らない。使い始める場合は、あわせてアップロードの手順を足す

## Slack 通知（Cloud Functions）

### 通知する出来事

| 出来事 | 通知するか |
|-------|----------|
| 新しいクラッシュ（初めて見る問題） | 通知する |
| 再発（解決済みにした問題が、また起きた） | 通知する |
| 急増（同じ問題が短時間に多く起きている） | 通知する |
| 新しい非致命的エラー | 通知する（ユーザー決定 2026-11-08） |

### 文面

- 日本語で送る
- 先頭に、開発・本番のどちらで起きたかを付ける（例:「【本番】」）
- 次を載せる: 出来事の種類、問題の名前、発生箇所、OS（iOS / Android）とアプリのバージョン、Firebase コンソールの Crashlytics の画面へのリンク
- 再発では、解決済みにした日時も載せる。急増では、件数と割合、最初に起きたバージョンも載せる

### 開発と本番

- CI は Cloud Functions を開発・本番の両方のプロジェクトにデプロイするため、関数は両方で動く
- 送り先のチャンネルは開発・本番で分ける（ユーザー決定 2026-11-08）

| プロジェクト | Slack のチャンネル |
|------------|------------------|
| 開発（`word-pods-dev`） | `#word-pods-app-alert-dev` |
| 本番（`word-pods-prod`） | `#word-pods-app-alert-prod` |

### 送り先の URL の管理

- Slack の Webhook URL は、知っていれば誰でもそのチャンネルに投稿できるため、コードや Git に書かない
- Google Cloud の Secret Manager に `SLACK_WEBHOOK_URL` という名前で保管し、関数は実行時に読む。開発・本番のプロジェクトそれぞれに登録する

### 送信に失敗したとき

- Slack への送信に失敗したら、関数をエラーで終わらせる（Cloud Logging にエラーとして残る）
- 再送はしない（Crashlytics の画面を見れば、問題そのものは確認できるため）

## プライバシーの申告

- App Store Connect の「App のプライバシー」で、次を申告する。トラッキングにはどれも「使用しない」
  - 「クラッシュデータ」「その他の診断データ」: 目的は「アプリの機能」、ユーザーへの紐付けは「あり」（uid を付けるため）
  - 「製品の操作」（Analytics の見た画面など）: 目的は「アナリティクス」、ユーザーへの紐付けは「なし」（uid を付けないため）
- プライバシーポリシーの本文に、Crashlytics・Analytics（Google）に情報を送ることを書き足す。このブランチでは行わず、別の作業で行う（ユーザー決定 2026-11-08）。規約の版数を上げるかも、その作業で決める
- 申告と本文の更新が済むまで、このブランチの内容を含むバージョンを審査に出さない（申告と実際の収集内容が食い違うため）

## テスト

- アプリ側: 集めるか集めないかの判定、エラーの報告、uid の付け外し、非致命的エラーの報告、見た画面の記録を、Fake を使った単体テストで確かめる
- Cloud Functions 側: アラートの種類ごとの文面、Slack への送信、送信の失敗を、jest で確かめる（Slack には実際には送らない）
- 実機での確認: リリースビルドで、サンプル画面（開発者だけが開ける）の AppBar の「クラッシュテスト」ボタンを押してわざとクラッシュさせ、アプリを開き直して、Crashlytics と Slack に届くことを確かめる
- iOS のクラッシュは dSYM がそろうまで Crashlytics で「未処理」のまま保留され、Slack にも通知されない。dSYM はビルドごとに別物のため、確かめたビルドの dSYM がアップロードされていることを dSYM タブで確認する

## Firebase コンソール・Slack での設定（手作業）

- Slack: 通知用チャンネルを作り、Incoming Webhook の URL を発行する
- Firebase コンソール: 開発・本番の両方のプロジェクトで Crashlytics を有効にし、Google Analytics をプロジェクトに連携する
- Secret Manager: 開発・本番の両方のプロジェクトに `SLACK_WEBHOOK_URL` を登録する
- CI のデプロイ用のサービスアカウントに、秘密情報を使う関数をデプロイできる権限を付ける（初回のデプロイで権限不足になった場合）
