# メールアドレス確認 振る舞い仕様書

## 1. 機能概要

メールアドレスとパスワードで新規登録したユーザーに確認メールを送り、メール内のリンクを押して確認済みになるまで、
確認待ち画面（`/verify-email`）から先に進ませず、同期もしない。
新規登録画面の「アカウント作成」の後に送信完了ダイアログを表示し、閉じた後に確認状態に応じてホーム画面か確認待ち画面へ移る。
概要設計書は `docs/high_level_design/email_verification.md`。

## 2. データ定義

### 2.1 AppUser（追加する項目）

| 項目 | 型 | 説明 |
|------|----|------|
| emailVerified | bool | メールアドレスが確認済みか。Firebase のユーザーの `emailVerified` をそのまま写す |

### 2.2 入力ルール

該当なし（確認待ち画面に入力欄はない。新規登録画面の入力ルールは変えない）。

---

## 3. 画面仕様

条件は「前提データ＋操作」、期待される動作は観測点で書く。
「未確認のユーザー」は `emailVerified` が false のログイン中のユーザー、「確認済みのユーザー」は true のログイン中のユーザーを指す。
「確認状態の問い合わせ」は `EmailVerificationRepository.reloadUser`、「確認メールの送信」は `EmailVerificationRepository.sendEmailVerification`、
「ログアウト」は `AuthRepository.signOut` の呼び出しを指す。

## 7. 対象外

- **Firestore のルール**（`users/**` の読み書きに確認済みを条件とする）: Flutter のテストではなく、`functions/test/firestore_rules.test.ts` で確かめる
- **既存ユーザー**: 一括で確認済みにする処理は行わない（概要 §既存のユーザー）。既存ユーザーも未確認なら新規ユーザーと同じ動作になり、本仕様書の各項目で確かめられるため、専用の項目を作らない
- **Firebase コンソールの確認メールのテンプレート**: 手作業の設定のため
- **`FirebaseAuthDataSource` の確認状態の取り直し**（ログイン情報（ID トークン）の更新 → ユーザーの取り直し → `authStateChanges` への通知の順序）: Firebase SDK を直接呼ぶだけの薄い層で、単体テストでは Firebase を動かせないため。実機で確かめる。`authStateChanges` が確認済みを流した後の画面の動きは EMV-K12・EMV-G04、同期の開始は EMV-Y03 で確かめる
- **`NotFoundFailure`**: 5章のどの code も `NotFoundFailure` に変換しないため、3.6 に行を作らない
- **ログアウトの `AuthFailure`・`TooManyRequestsFailure`**: ログアウトは Firebase の認証サーバーに問い合わせず、これらの失敗を返さないため
- **送信完了ダイアログを閉じた後の問い合わせの `UnknownFailure`・`TooManyRequestsFailure`・`AuthFailure`**: どの失敗でも「画面の移動の停止を解く」だけで動作が変わらないため、代表として `NetworkFailure`（EMV-A09・EMV-A15・EMV-V08）を書いた。`AuthFailure` の場合も、ここではログアウトせず、確認待ち画面の表示時の問い合わせ（EMV-E07）でログアウトする
- **送信完了ダイアログの「閉じる」の二重操作**: 1回目のタップでダイアログが閉じ、2回目はタップできないため
- **新規登録の作成の失敗（`AuthFailure` 以外）**: 今までの新規登録画面の動作から変えない（`legal_consent.md` の新規登録の仕様のまま）。EMV-A10 は「確認メールを送らない」ことを確かめるための代表
- **ログイン画面・LoginViewModel**: 変えない。LoginViewModel は今までどおり、ログインの成否・同期の成否によらず、ログインの処理が終わったら画面の移動の停止（`authSyncInProgressProvider`）を解く（未確認の間は同期が `syncUserId` で止まるため、すぐ終わる）。その後の移動先は `authRedirect`（停止中は EMV-G14、解いた後は EMV-G06）、ログイン直後の同期を止めることは `syncUserId`（EMV-Y08）で確かめる
- **新規登録の「アカウント作成」の二重操作・入力の制約**: 新規登録画面の今までの動作（処理中は「アカウント作成」を押せない・入力チェック）から変えない。処理中の期間に確認メールの送信が加わることは EMV-A18・EMV-V54 で確かめる
- **スプラッシュ画面**: 変えない（起動時に確認状態の問い合わせを待たないことは、スプラッシュ画面に問い合わせを加えないことで満たす）。未確認のユーザーでスプラッシュからホーム画面へ移ろうとしたときの振り替えは EMV-G01 で確かめる
- **Google ログイン**: 最初から確認済みとして扱われ、今までの動作から変わらない
- **端末への確認済みの保存・オフラインでのホーム画面**: Firebase SDK がログイン情報を端末に保存する動作で、アプリの処理ではないため
- **Mock モード**: 開発用の Mock（`MockAuthRepository`・`MockEmailVerificationRepository`）は Firebase なしで画面を確かめるためのもので、テスト対象外（CLAUDE.md の除外）
- **今回やらないこと**（ワンタイムコード・SMS・ディープリンク・独自の確認完了ページ・未確認アカウントの自動削除）: 実装しないため
- **入力の境界・同じ値・対象の不在**: 確認待ち画面に入力欄はなく、操作する対象（データ）もないため
- **確認待ち画面のキャンセル・外側タップ**: 確認待ち画面の操作はダイアログを開かないため
- **確認待ち画面での OS の戻る操作**: 戻る先の画面が無く、OS の標準の動作（アプリを閉じる）に任せるため（8章 Q2）
- **ログアウトの応答待ちの間に問い合わせが確認済みを返した場合**: ログアウトが優先され、ログイン画面へ移る。どちらも Firebase のログイン状態の変化で決まり、アプリの処理の分岐が無いため
- **送信完了ダイアログを閉じた後の問い合わせの失敗をユーザーに伝えること**: 概要 §確認メールの送信完了ダイアログで「何も表示しない」と定めている（原則-2 の例外。8章 Q6）。失敗しても移動先の確認待ち画面でやり直せるため
- **同意ダイアログとの関係**: 送信完了ダイアログの表示中は、画面の移動を止めている（`authSyncInProgressProvider` が true）ため、同意の判定は行われない（`legal_consent.md` §判定のタイミング）。閉じた後の判定は規約同意の仕様書の範囲
